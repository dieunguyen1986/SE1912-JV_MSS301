Software Architecture Design

Job Service Architecture

This document describes the job-service in a simple and production-style way. It is written for newcomers, so the structure is easy to follow while still reflecting a real-world system.

Spring Boot REST API Domain-Driven Structure JPA + PostgreSQL Audit Support Health & Info Endpoints

1. Purpose

The job-service manages job post lifecycle, department data, and skill data. It exposes REST APIs for internal and public consumers and stores data in PostgreSQL.

The service is designed with clear layers so business rules stay separate from web and database concerns.

2. Key Responsibilities

Job management — create, update, submit, approve, publish, close, delete
Reference data — departments and skills
Search and list — keyword filtering and pagination
Operational support — health, info, correlation ID, and error handling

3. High-Level Architecture

The service uses a Ports & Adapters (Hexagonal / Clean) structure. The most important idea is the Dependency Rule: all dependencies point inward, toward the Domain. The Domain is the center and depends on nothing.

Two things flow in different directions, so read the arrows carefully: the blue arrows show the call flow at runtime (a request travels down toward the database), while the green arrow shows a code dependency (Infrastructure implements an interface owned by the Domain — this is Dependency Inversion).

Why the green arrow points up: the Application calls the JobRepository interface, which lives in the Domain. At runtime Spring injects JobRepositoryAdapter (Infrastructure) as the implementation. So the Domain never knows JPA or PostgreSQL exist — the database is a swappable detail, not something the Domain depends on. This single inversion is what makes the design "Clean".

4. Request Flow

1. API receives request — validation is applied at the boundary.
2. Controller delegates to use case — the controller stays thin and does not contain business rules.
3. Use case executes business logic — it works with domain objects and calls a port (e.g. JobRepository), never JPA directly.
4. Adapter implements the port — JobRepositoryAdapter fulfils the interface using JPA, so the domain stays free of framework details.
5. Response is mapped back to API DTO — stable output for clients.

6. API Layer

The API layer handles HTTP requests, validation, and response formatting. It keeps endpoint logic simple and readable.

7. Domain Layer

The domain layer contains the core business model and the ports (repository interfaces). This is where the job lifecycle and rules belong, and it depends on no other layer.

8. Infrastructure Layer

The infrastructure layer connects the domain to JPA and PostgreSQL through repository adapters.

9. Operational Design

Component Production intention
Auditing Records the actor for data changes. The current setup uses a default system user.
Exception handling Centralized error mapping helps API responses stay consistent.
Correlation ID filter Improves tracing across logs and requests.
Actuator Provides health and info endpoints for monitoring and operations.
Validation Protects the service boundary with request validation before business logic runs.

10. Production Notes

Current development setup

The application is configured with spring.jpa.hibernate.ddl-auto=update for local development. In a production environment, schema changes should be managed with a migration tool such as Flyway.

Suggested production principles

Keep the controller thin, keep domain rules inside use cases and entities, and keep database access behind repository adapters.

Known pragmatic compromise: the domain ports currently return Spring Data Page/Pageable — a small framework leak into the domain. It is acceptable for a small project; a stricter Clean Architecture would expose a framework-free paged result instead.

This design is intentionally simple, but it already reflects a production-friendly structure: clear layers, stable contracts, and operational visibility.
